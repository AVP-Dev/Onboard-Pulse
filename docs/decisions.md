# Architecture Decision Records (ADR) - Onboard Pulse

## ADR-001: Использование встроенного модуля node:sqlite вместо внешних СУБД или нативных биндингов
- **Контекст:** Требуется надёжное локальное хранение данных на macOS с поддержкой ACID-транзакций, отсутствием сетевых зависимостей и сохранением между перезапусками процесса.
- **Решение:** Использовать встроенный в современный Node.js модуль `node:sqlite` (`DatabaseSync`).
- **Последствия:** Zero external services, zero build/compilation issues на Darwin ARM64/x64, строго синхронные транзакции, файловая персистентность в `data/pulse.db`.

## ADR-002: Детерминированный Rule Engine вместо LLM для выявления проблем
- **Контекст:** Ограничение задачи: не использовать LLM для принятия кадровых решений. Анализ оценок должен быть прозрачным и предсказуемым.
- **Решение:** Прозрачные правила:
  - Оценки 1–2: критический сигнал (`CRITICAL`).
  - Оценка 3: сигнал внимания (`ATTENTION`).
  - Оценки 4–5: норма (`NORMAL`).
- **Последствия:** Мгновенный отклик, 100% повторяемость, лёгкое модульное тестирование, отсутствие галлюцинаций.

## ADR-003: Одноразовые криптостойкие токены анкет
- **Контекст:** Новичкам отправляются персональные ссылки для прохождения опроса. Необходимо исключить угадывание ссылок, повторное заполнение и подмену данных.
- **Решение:** Генерация UUIDv4 для каждого опроса, статус `is_completed = 1` при отправке, атомарная проверка в транзакции `BEGIN IMMEDIATE`.
- **Последствия:** Исключение дублирующих отправок и несанкционированного доступа.

## ADR-004: Строгий инвариант верифицированного закрытия проблем
- **Контекст:** Проблемы новичков часто закрываются формально («галочка» от наставника без реального решения).
- **Решение:** Проблема не может быть переведена в статус `CLOSED` без обязательного повторного опроса сотрудника (re-check) с оценкой по проблемной категории не ниже 4. Если оценка 1..3, статус возвращается в `IN_PROGRESS`.
- **Последствия:** Реальный контроль устранения проблем, снижение раннего оттока на испытательном сроке.

## ADR-005: Сетевая топология Docker, изоляция томов и healthcheck в Coolify / Traefik
- **Контекст:** При развёртывании в production-окружении Coolify с обратным прокси Traefik и Cloudflare возникали:
  1. Ошибка сборщика из-за попытки копирования игнорируемой директории `data/`.
  2. Изоляция контейнера в приватной bridge-сети Docker Compose вместо общей сети `coolify`.
  3. Коллизия стандартного порта 3000 на сервере.
  4. Ложный статус контейнера `unhealthy` из-за GET-запроса healthcheck к эндпоинту `/api/dev/seed`, принимавшему только POST.
- **Решение:**
  1. В `Dockerfile` заменить `COPY data` на `RUN mkdir -p /app/data` и добавить очистку кэша Webpack (`rm -rf .next/cache`).
  2. В `docker-compose.yaml` подключить контейнер к внешней сети `coolify`.
  3. Сделать порт хоста конфигурируемым с нетривиальным дефолтом (`${HOST_PORT:-3088}:3000`) и убрать статичный `container_name`.
  4. Добавить GET-обработчик в `/api/dev/seed` и перевести healthcheck на рабочий эндпоинт `/api/employees`.
- **Последствия:** Автоматический запуск, мгновенное обнаружение сервиса обратным прокси Traefik, выпуск SSL-сертификата и стабильная работа.
